# 地点搜索排序

## 问题与范围

原搜索按“完整店名、名称包含、类目包含、描述包含、最新 ID”的固定层级取前若干条，随后才附加距离。附近的类目匹配因此可能输给远处的名称包含；在截断之后补距离也无法找回已经漏掉的候选。

本次在现有 SQLite 搜索中联合文字相关性、地图中心距离和避雷状态排序。保留同步接口 `fastSearch(query, limit, options = { center })` 的旧调用兼容性，不增加模糊纠错、语义模型或搜索服务。

## 匹配与避雷语义

1. 查询、名称、类目、描述使用同一字面归一化：NFKC、转小写、移除空白、标点和符号。因此全半角、大小写、排版标点差异不妨碍匹配，`%`、`_` 等输入也不作为通配符。
2. 查询先按空白、英文逗号、中文逗号、顿号和分号拆词，再归一化。每个非空词都必须命中名称、类目或描述之一；不同词允许命中不同字段。连续中文不自动分词。
3. 完整查询经紧凑归一化后等于完整名称时，视为精确店名，优先级最高，包括避雷店名。
4. 避雷状态复用共享的 `isAvoidedPlace` 规则：有评分时，平均评分 `< 2.5` 才是避雷；无评分时，以类目包含“避雷”为准。有评分时不再使用类目标签覆盖评分判断。
5. 普通查询把避雷地点排到普通地点之后，不删除候选。独立的“避雷”查询词作为显式筛选条件，先移除该词，再匹配其他词，并只返回避雷地点。例如“避雷，火锅”可以找到评分较低但没有避雷标签的火锅店。“避雷火锅”不是独立筛选词，按普通文字匹配处理。

## 计分与稳定排序

对每个查询词 `t`，取所有命中字段中的最高分，再对所有词求平均，得到 `textScore`。

| 命中方式 | 单词得分 |
| --- | --- |
| 名称包含 | `100 + 5 × (归一化词长 / 归一化名称长)` |
| 精确匹配一个类目项 | `95` |
| 类目包含 | `90` |
| 描述包含 | `55` |

有有效中心点和地点坐标时，以千米距离 `d` 计算：

```text
geoBonus = 30 × 2 ^ (−max(0, d − 0.3) / 15)
totalScore = textScore + geoBonus
```

300 米内地理加分均为 30，之后每增加 15 公里减半，使同城约 20 公里内的直接类目匹配仍可超过跨城的名称包含。中心点或地点坐标无效时不加地理分；未提供有效中心点时仅使用文字计分。

距离加分上限保留了明确的文字相关性底线：单词仅在描述中出现时最多为 `55 + 30 = 85`，仍低于类目包含的 `90`。附近奶茶店在描述中提到“烧烤”，不会因此超过真正分类为烧烤店的结果。精确名称仍使用单独的最高优先级。

最终依次比较：精确店名优先、普通地点优先于避雷地点、总分降序、有效距离升序、解析后的创建时间降序、ID 降序。缺少有效距离时不获得距离优势，缺少有效时间时使用固定回退值，确保同一输入顺序确定。显式避雷查询的候选本身均为避雷地点，仍按其余规则排序。

SQLite 注册确定性的文字归一化 UDF，使召回与计分使用相同的字面规则；SQL 参数化匹配所有候选，不在联合排序前设置候选数量上限。完成排序后才应用 `limit`，返回上限为 100。

## 示例与接口行为

以下均为合成示例，查询为“火锅”，未命中完整店名：

| 地点 | 匹配与距离 | 近似总分及结果 |
| --- | --- | --- |
| 近处餐馆 | 类目项为“火锅”，200 米 | `95 + 30 = 125`，可排在远处名称包含之前。 |
| 远方火锅 | 名称包含“火锅”，20 公里 | `102.5 + 12.07 ≈ 114.57`。 |
| 某避雷火锅店 | 名称包含，100 米，平均分低于 2.5 | 即使数值分较高，也排在普通地点之后；搜索“避雷 火锅”仍可找到。 |

直接搜索某家店的完整名称时，精确名称优先于上述分数与避雷降权，用户仍能定位该店并查看原有警示。

现有搜索路由及别名都向同一服务转发 `center`，响应继续使用数组。提供有效中心点时，结果保留 `distance_km`；地点坐标无效则该值为 `null`。前端保留服务端返回顺序。中心点取发出请求时的当前地图中心，平移地图不会自动重新搜索；再次提交搜索才使用新中心。

## 验证

2026-10-15 已通过：

- `backend/` 的 `npm run test:search`：20 个关键词排序回归用例，以及原搜索烟测。AI 密钥在测试中主动禁用，原烟测验证其不可用时仍保留基础搜索。
- `backend/` 的 `npm run test:qq-bot`、`npm run test:ratings`：同步旧调用、首结果卡片、评分与避雷规则兼容。
- `frontend/` 的 `npm test`、`npm run build`：原前端测试与生产构建；构建保留原有分包大小和混合导入提示。

回归重点覆盖归一化与通配符输入、多词跨字段匹配、精确店名、避雷共享规则及显式筛选、城内与区域距离的影响、先排序后截断、无效坐标、时区明确的日期平局和旧调用兼容性。
