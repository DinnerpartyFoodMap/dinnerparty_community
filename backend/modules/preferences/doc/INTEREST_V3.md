# 个人主页与兴趣信号 v3

## 主页故障

用户日志中的主页 500 来自 `Taste inputs changed`：旧实现以整个连接的 `total_changes/data_version` 判定偏好输入变化，又在请求中重置共享均值缓存并等待远程批量求均值，后台无关画像写入即可令两次重试都失败。

现在使用独立 `TasteAxisClock`，分别跟踪原型输入和评价/收藏/行为/手填偏好。模型画像进度、其他无关写入不使六维缓存失效。向量均值与原型在同一次本地同步读取中构造，不再重置共享均值缓存或请求远程均值。真实相关数据持续变化时重新读取；最后使用新鲜的本地评价/手填结果，不让可选向量估计拖垮整个主页。

同一服务器快照临时副本，后台每 10ms 写画像元数据，并发加载评价历史最多的三位住民：全部成功，首次合计约 1.35s，缓存后约 0.25s。本机单次诊断不代表生产网络或设备性能。

## 保守的六维刻度

保留所有符合原策略的创建/导入默认评价，不区分展示来源。手填等级保持原值并优先。自动分数改为 `taste-axes-v3`：

- 直接证据向中性收缩，先验强度从 2 提高到 6，不再被全站高分先验整体抬高。
- 评价信号减去本人平均评分信号的一半，保留绝对喜好，同时降低“所有店都打高分”对六维的共同抬升。
- 收藏仅是弱兴趣；向量百分位保留原始字段，但显示值根据有效证据量向 0.5 收缩。少量证据不轻易显示强烈偏好。
- 有效的低百分位、零值仍是有效数据；自动低值仍统一显示“一般”，不显示推断依据或估算/手填来源。

这是保守的产品刻度调整，不是已经通过前瞻实验验证的准确率提升。

## 采集与消费

| 信号 | 采集 | 参与偏好 |
| --- | --- | --- |
| 详情打开 | 已登录且启用交互记录，详情在前台可见 800ms 后记 `detail_open` | 很弱兴趣，不能当作首选命中或到访 |
| 详情浏览时长 | `detail_dwell`，只累计网页/iOS 前台可见时间；切后台、关闭、换点时结算；至少 5s、单段最多 5min | 按时长递增但有上限的弱兴趣 |
| 收藏/取消收藏 | 原 Favorite 与行为事件继续记录 | 当前收藏比点击/浏览更强；取消后不当成仍收藏 |
| 导航 | 原 `navigation` 继续记录 | 兴趣线索，不等于真实到访或好评 |
| 评价 | 原四档评价与默认历史保留 | 强于软行为；明确差评不被点击/浏览/导航抵消 |

网页和 iOS 共用生命周期计时，后台时间、预加载、未标记外部 POI、未登录和未启用交互记录不计入。事件按原有 event_id 幂等及 30 分钟同店同类型冷却；重复操作不会不断加分。单店六维使用最强软信号而非无限叠加，导航/浏览不制造评分。

新信号进入六维、私有服务口味向量和现有研究导出；浏览时长保存在 `duration_ms`。沿用原授权、研究许可和 90 天清理规则，不补造过去没有采集的浏览记录。现有 4B 评分/首选树未因此重新训练；未来训练需要实际评分与真实选择标签，不能把打开详情自动当正样本。

`/api/visits/status` 仅报告到访推断功能是否启用。客户端先查询状态，关闭时不再对每个点发送必然返回 503 的查看请求。普通点击/浏览采集不依赖开启定位到访功能，原“是否去过”确认流程仍保留。

## 部署

配套私有服务 `main` 提交：`3a048e8`。既有 4B 模型包和 embedding 配置保持不变。

先更新私有 Node 服务，再更新后端，最后发布网页/iOS 客户端。后端自动迁移旧 `UserBehaviorEvent`，保留原事件 ID、数据、索引、触发器和自增序列，增加两种事件和时长字段。部署前照常备份数据库。

这次包含前端采集代码，iOS 需要重新构建发布客户端；不需要 Python、Torch，也不需要重训 4B 模型。旧客户端仍能提交原有收藏和导航，但新增点击/时长要更新客户端后才开始积累。

验证：66/66 后端测试、72/72 私有 Node 测试、前端评价/到访单元测试与网页/移动端构建通过。包括前后台时长排除、重复清理不双计、时长范围校验、幂等和冷却、软信号不能覆盖差评、默认评价保留、手填覆盖、无关写入不使六维失效。服务器快照旧有 215 条行为记录迁移后逐字段一致。iOS 尚未进行 Xcode/真机验证。
