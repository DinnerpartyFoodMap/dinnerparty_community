# 六类餐饮偏好（住民主页雷达）

实现：`services/tasteAxes.js`；接口：`GET /users/:id/profile` 的 `taste`、`PUT /users/me/taste`、管理员 `/admin/taste-axes/places`。

每一轴回答“你有多喜欢这类餐饮”。各轴独立，不求和、不算面积、没有总分；所有住民用同一刻度。

| 轴 | key | 例子 |
| --- | --- | --- |
| 家常正餐 | `homestyle` | 家常菜、地方菜馆、中式正餐 |
| 粉面简餐 | `noodles` | 面馆、米粉、盖饭、快餐、茶餐厅 |
| 火锅烧烤 | `hotpotBbq` | 火锅、串串、烤肉、烧烤 |
| 甜品烘焙 | `dessert` | 蛋糕、面包、冰淇淋、糖水 |
| 咖啡茶饮 | `drinks` | 咖啡、奶茶、茶馆 |
| 异国料理 | `foreign` | 日料、韩餐、西餐、东南亚菜 |

“轻食蔬食”在现有地图里只有约 20 家店（大多是“中式素菜馆”），先换成覆盖约 170 家店的“异国料理”。改轴时同步 `TASTE_AXES`、`CATEGORY_RULES`、前端 `src/profile/tasteAxes.js` 和文案 `profile:taste.axes.*`。

## 1. 店铺分类

优先级：人工纠正 > 规则 > 模型。

- 规则：分类名包含关键词（`CATEGORY_RULES`），或店名里有不易误判的强关键词（`NAME_RULES`）。一家店可以属于多轴。
- 模型：规则判断不了的公开地点由后台每 15 分钟一批交给 DeepSeek（`startTasteClassificationWorker`），只看店名、分类和简介，拿不准时返回空数组 = 未知。结果按内容摘要（`input_hash`）缓存，店名、分类或简介改了才重新判断。
- 人工：管理员后台“店铺口味分类”（`manage_places`）列出未知 / 模型分的店，勾选所属类；可撤销，回到规则与模型。

结果存在 `PlaceTasteClass`（只存模型与人工结果，规则每次现算）。

## 2. 住民反馈

- 评价是主要依据：只算住民自己打的评价（`PlaceRating.source = 'user'`）。创建时自动写入的评价（`create`）和建表时按创建者补的评价（`migration`）都来自“创建地点”，不算偏好。
- 收藏是较弱的兴趣线索：只收藏没评价的店算一份权重 0.35、倾向 0.5（“有兴趣”，不等于明确好评）的证据；评价过的店再收藏不重复计。
- 创建、修改地点不加分。同一家店在同一轴只算一份证据。

## 3. 每轴分数

评价四档映射到 -1…1（`(score - 2.5) / 1.5`），每轴按证据权重平均，再以权重 2 向全站在这一轴的平均倾向收缩（样本少时不会一次好评就满分），最后映射到 0–1 显示。全站倾向本身也以权重 10 向中性收缩：全站评价还少时，几条好评不会把所有人的先验都拉高。没有任何证据的轴返回 `null`（“待了解”），不画成 0。

## 4. 夹角估算（补位）

某一轴没有直接证据时，用口味方向估算：`s_k = cos(u, t_k)`。

- 向量：都是 `place_vectors` 里同一个 embedding 模型的地点向量。
- `t_k`：这一类全部店铺（规则 / 模型 / 人工分出来的）的向量之和，多类的店按类数均分。用典型店铺构造，不只编码类名几个字。
- `u`：住民自己的评价与收藏对应店铺向量的加权和（好评正向、差评反向、收藏权重 0.35）。不用 `UserPreference` 里的画像向量：那份画像含创建时的评价、导航和分享，是“接触”不是“喜欢”。
- 去掉共同的“餐饮”方向（减全部地点的平均向量）：按本地数据（1435 家店、934 家单类店）验证后选择。不去掉时六类典型方向两两余弦平均 0.84（最高 0.94），几乎分不开；去掉后为 -0.15。用“3 家同类店 + 1 家随机店”的模拟住民检验逐轴标定后的最大轴：去掉 0.93、不去掉 0.91，去掉后余弦的离散程度约是 5 倍（标准差 0.19 对 0.04）。单店最近类准确率不去掉略高（0.87 对 0.83），但雷达是按住民比较，以模拟住民为准。
- 逐轴标定：余弦 0.8 不等于“80% 喜欢”。每一轴拿“随手挑同样多家店”的随机口味做参照（证据数分组，每组 300 个、固定种子），把 `s_k` 换算成比多少比例的随机口味更偏向这一类（`percentile`）。
- 只在高于一半时作为依据，显示值就是这个比例；低于一半仍是“待了解”，低相似度不当成讨厌。
- 代表店铺只列住民有好感、且确实接近这一类方向的店；没有就不列。

优先级：自己填的 > 这一类店的直接评价 / 收藏 > 夹角估算 > 待了解（`basis` 字段：`self` / `evidence` / `embedding` / `null`）。

住民可以给某一轴自己填喜好（与评价同样的四档），存在 `UserTastePreference`，覆盖自动推断；清除后回到自动推断。

后续可加：住民打分宽严校正、店铺质量校正（下文评估里两者都试过，现阶段数据下没有改进）。

## 5. 用后端快照的评估（2026-10-28）

快照：3252 家公开店（全部有向量），规则分出 76%；住民自己的评价 406 条（131 人，61% 是“强烈推荐”，人均约 3 条），收藏 142 条。

**轴的方向（t_k）**

| 方法 | 单店 AUC（5 折） | 六类方向两两余弦（均值 / 最大） | 模拟住民准确率 | 真实住民留一（逐轴 AUC 均值） |
| --- | --- | --- | --- | --- |
| 当前：减平均向量后求和 | 0.961 | -0.16 / 0.45 | 0.95 | 0.584 [0.536, 0.633] |
| 带 x 标签的均值 − 不带的均值 | 0.961 | -0.15 / 0.49 | 0.95 | 0.583 |
| 与其他类对比 | 0.963 | -0.17 / 0.49 | 0.95 | 0.586 |
| LDA（收缩协方差）/ 岭回归 | 0.993–0.994 | -0.03 / 0.05 | 0.98 | 0.561 [0.518, 0.606] |
| 只数证据（不用向量） | — | — | — | 0.577 [0.531, 0.620] |

“带 x 的均值减不带 x 的均值”与当前做法方向相同：mean(带) − mean(全部) = (N−n)/N · (mean(带) − mean(不带))，只差一个正的倍数，余弦不变（实测逐轴余弦 0.987–0.998）。LDA / 岭回归把店分得更开、六类方向几乎正交，但描述真实住民没有更好（与当前之差 -0.023，95% 区间 [-0.055, +0.014]），雷达里各轴的差别反而更小（住民内标准差 0.264 对 0.292），所以保留当前做法。

**显示刻度**：当前刻度下真实住民的值大多在 0.7–0.9（“喜欢 / 很喜欢”），一个人的各轴差别很小（住民内标准差 0.047）。试过：按住民打分宽严校正、按店铺质量校正、两者都做（都更平）、逐轴换算成在住民里的名次（住民内标准差 0.14，但只是放大噪声：大多数人只有一条“强烈推荐”，名次堆在一起，评过 21 家、平均 3.52 分的住民在家常正餐上排到 0.12）。留一检验里没有哪种刻度能预测住民对同一类下一家店的评价（Spearman 都在 0 附近，区间跨 0），所以保持当前刻度。

**原因**：用矩估计拆出住民之间真实的口味差异（τ）与单条评价的噪声（σ）：去掉打分宽严后，只有火锅烧烤有可检出的住民差异（τ 0.44），家常正餐、粉面简餐原来的差异是打分宽严，甜品烘焙、咖啡茶饮、异国料理 τ 为 0。现在的数据量下，雷达各轴本来就分不太开；想让它更有区分度，靠的是更多住民自己的评价，而不是换算法。评价多起来后，可以改为显示“比一般住民更喜欢的把握” P(θ > μ)（正态先验 + 评价噪声，τ、σ 由上面的矩估计得到），它在证据不足时自动停在 0.5，证据够了才拉开。

另：规则判断不了的店占住民证据的 19%；用岭回归在 90% 精度下能再给 790 家未知店里的 290 家打上类，可作为模型分类之外的补充。

## 返回字段

`taste` 是六项数组，每项：`key`、`value`（显示用，null = 待了解）、`basis`（这一轴的依据）、`inferred`（直接证据推断）、`embedding`（夹角估算：`value`、`percentile`、`cosine`、`shop_count`，没有向量时为 null）、`self_level`、`store_count`（有效店铺数）、`positive_count` / `negative_count`（明确好评 / 差评次数）、`favorite_count`、`sources`（`self` / `rating` / `favorite`）、`places`（最多 3 家代表店铺，只有 id、店名、自己的评价和是否收藏，不带坐标）。
