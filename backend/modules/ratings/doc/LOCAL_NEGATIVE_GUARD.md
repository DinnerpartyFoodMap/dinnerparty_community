# 本地负面评价与社区避雷保护

## 产品规则

`local-negative-guard-v1` 针对两类地点生效：社区分类含精确“避雷”标签，或真实有效评价中 1/2 分严格超过一半。默认、创建、导入评价仍保留原来的一份投票，不加假人数。普通地点不满足条件时，原综合估计与本人预测保持原路径。

受保护地点的综合估计改用 2.5 中性先验（强度 2）；1 分权重 2、2 分权重 1.5、3/4 分权重 1。沿用既有评价者宽严拟合，但单条校正最多 ±0.25，最终不超过 2.4，避免跨入“均线之上”。没有真实评价时仍显示无可用分，不用标签编造投票或分数。

受保护地点的本人预测以当前公开的本地估计为基准，叠加冻结模型的“本人输出−中性本人特征输出”差值；差值限于 ±0.5，并按本人历史数 `n/(n+5)` 收缩，最终不超过 2.4。树特征及历史偏差仍排除本人对目标店的评价；最终产品保护有意读取公开投票共识，不能用这一步宣称独立留出预测精度。

社区“避雷”标签始终保留地图警示，不能被模型生成的 Restaurant 等分类覆盖。随机与 AI 推荐排除显式避雷、原始低于均线或负评占多数的地点。地点仍可被按名称查询、在列表中查看。发现标签过时或错误时，走已有地点编辑/审核流程修改；未标记地点负评不再占多数时自动恢复原算法。

网页和 iOS 共用的地图标记逻辑已同步。已有投票分布、两分展示、90 天记录规则、首选五名隐藏加成不变。

## 研究依据与取舍

先登记 `research/rating-confidence/results/round12/p102-registration.json`，再运行点评两个时间块与 Google 开发块，保留全部消融。最初的全局降先验/负面加权方案没有通过预设门槛，已撤出产品。用户随后明确要求公开数据不过门槛也要解决本地问题，补记 `p102-product-amendment.json`，采用上述定向产品约束。

该策略不声称提高全域未来均分预测精度：Google 开发集总体 MSE 从 0.074152 到 0.112154（约 +51.25%），点评两个块约 +5.28% / +2.94%。早期低分后口碑回升的店会受影响；这里只为当前本地显式警示和负面共识提供保护。未来增加好评、移除过时标签后，保护状态会相应变化。

用户快照在临时副本回归，使用原冻结 4B 模型、固定评估时间，以及评价历史最多的一位用户：

- 247 个地点满足保护条件，其中显式避雷 148 个；综合分跨入推荐区从 159 个降到 0，本人 ready 预测从 198 个降到 0。
- 其余 3265 个可见普通地点的综合分与该用户的预测分逐项完全相同；投票人数与分布全部不变。
- 鹿其林酒家 `[2]`：综合约 2.393、该测试用户预测 2.4。
- 广州大学火龙果肠粉 `[1,1,4]`：综合约 1.837、该测试用户预测约 1.933。

这位测试用户未被认定为截图账号，不能把其预测值当成截图账号的精确复现。原截图 3.2 与旧快照 2.3 的分组差异也已诊断：把旧“避雷”分组换成普通分类，原公式可回升到约 3.2；新保护读取独立社区标签，不依赖这个分组。

## 首选模型执行检查

真实本地 HTTP 和冻结 4B 模型回归通过：列表对完整候选集调用一次首选模型，再分页；首选五名分别加 0.30 / 0.24 / 0.18 / 0.12 / 0.06，只影响排序，不显示为评分。随机使用 choice score 调整抽样概率，不加列表的五名加成；冷却过滤后仍保留至少 20% 基础探索。开启状态为 `RATING_LIST_RANK_MODE=active`、`RATING_RANDOM_RANK_MODE=active`（未设置也默认 active）。`off` 禁用，`shadow` 只运行不替换结果；私有服务不可用时回退。

这是本地代码/请求验证，不能证明远端生产服务器的部署版本或配置。原模型包、特征和链店排除策略不变。
