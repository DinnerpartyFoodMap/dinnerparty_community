# 地点评价

每个注册用户都可以给已收录的地点评价，不需要审核，有每日次数上限。不打星、不写分数，只选四档评价词；分数只用来求平均。

| 分数 | 评价 | 说明（界面提示） |
| --- | --- | --- |
| 4 | 强烈推荐 | 值得专程去吃 |
| 3 | 均线之上 | 路过可以吃 |
| 2 | 均线之下 | 不太值得去 |
| 1 | 强烈拒绝 | 避雷，别去 |

## 参考与取舍

- 鸭觅：不给千篇一律的综合分，按每人口味算“专属匹配度”，并能看到与其他用户的口味相似度；“金勺子”用愿意跑多远来表达档位（顺路 / 绕路 / 专程）。这里借用了后两点：每档配一句行为化的说明，登录用户额外看到按口味加权的分数。
- 大众点评：精选评价攒够 10 条才计算并展示星级，并按评价者的可信度、时间、质量加权。这里社区小，不隐藏分数，而是在少于 3 人评价时注明“评价较少，仅供参考”；被封禁用户的评价不计入。
- Beli：只有“喜欢 / 一般 / 不喜欢”三个按钮。这里同样只让人选档位，不让人纠结 1–10 分。
- 公开分数与口味加权并列显示，不互相替换：大家在群里说“这家 3.2”时看到的是同一个数。

## 数据

- `PlaceRating(place_id, user_id, score, source, weight, created_at, updated_at)`：每人每店一条，改评覆盖。`source` 为 `user`（评价接口）、`create`（添加地点时的创建者评价）或 `migration`（上线时由已有地点生成）。`weight` 保存评价者权重与该条评价时间衰减的乘积 `W × τ`。删除地点或用户时级联删除。
- `UserReputation`：保存每个用户的贡献系数 `β`、一致度系数 `γ`、最终权重 `W`、证据量及更新时间，供每日批处理与新评价写入使用。个人权重不在界面展示。
- `RatingWeightRefresh`：保存最近一次成功批处理的时间；与用户声誉、全部评分权重在同一事务中提交，失败时完整回滚。
- `PlaceRatingEvent`：评价接口的操作日志（`rate` / `withdraw`），只用于每日次数；`place_id` 不是外键，地点被删也不退还当天已用次数。
- 上线迁移：首次创建 `PlaceRating` 表时，为每个创建者账号仍存在的已有地点写入创建者的评价——分类含“避雷”记 1 分（强烈拒绝），其他记 4 分（强烈推荐）。迁移时间取原地点时间，并显式解析旧数据的 `M/D/YYYY` 格式，避免将老评价记为上线当天。只在建表时执行一次；之后撤回的迁移评价不会在重启后回来。
- 新地点：网页/App 添加时表单里选择创建者评价，默认按标签预选（带“避雷”→ 强烈拒绝，否则强烈推荐），可以改；QQ 机器人与公开日记创建的地点按同样规则自动写入。创建者评价不占每日次数。

## 综合评价与避雷

- 汇总：人数、综合分、四档分布，均排除当前被封禁用户。综合分为 `Σ weight × score / Σ weight`；人数与四档分布仍按实际评价人数统计，不乘权重。综合分取最接近的一档作为评价词，正好一半时取较好的一档（2.5 → 均线之上）。
- 地图与各接口用同一规则判断“避雷”：有人评价时平均分 < 2.5（落在均线之下 / 强烈拒绝）；没人评价时看分类是否含“避雷”。地图标记的避雷图标、聚合成员列表的红色店名、海报标记、随机美食、AI 推荐与顺路吃的默认过滤都按这条规则。“避雷”标签本身保留为普通分类。
- `/places`、`/places/nearby`、`/places/:id`、新增/编辑地点的响应、关键词搜索、AI 搜索、顺路吃和随机美食的地点行都带 `rating_count` 与 `rating_average`。

## 评价权重

一条用户 `v` 对地点 `p` 的评价使用以下权重；`t` 是该条评价最后修改距今的天数：

```text
ω(v,p) = W(v) × τ(t)
W(v)   = β(v) × γ(v)
τ(t)   = 0.6 + 0.4 / max(1, log₃₁(t + 1))
```

新评价与刚改过的评价 `τ = 1`。时间衰减按最后修改时间计算，随着评价变旧逐渐减小，五年时约为 0.78。`create`、`migration` 和 `user` 来源的评价都参与公开综合分与按口味加权分。

贡献系数 `β` 从仍存在的地点、对他人地点的主动评价和已采纳的修改申请计算：

```text
P = Σ 自己创建且仍存在的地点 [0.3 × C + 0.4 × f/(f + 5) + 0.3 × ln(1 + m)]
    + 0.1 × min(30, 主动评价过的他人地点数)
    + 0.5 × min(10, 被采纳的修改申请数)
C = 0.8 × 现有资料完整度 + 0.2 × (有外观或菜单图片 ? 1 : 0)
β = 1 − 0.5 × exp(−P/5)
```

`f` 是收藏该地点的其他用户数，`m` 是评价过该地点的其他用户数；都排除创建者本人和被封禁用户。对本人一致度的主动评价证据只认 `source = 'user'` 且本人不是地点创建者的评分；给自己创建的地点改评，即使来源变成 `user`，也不算本人的一致度证据。

一致度系数 `γ` 也只使用上述主动评价证据。对用户 `v`，地点 `p` 还必须有至少 2 名其他有效主动评价者。令 `N` 为满足条件的地点数，`r_p` 为 `v` 的评分，`s(v,o)` 沿用按口味加权的相似度：

```text
m_p = Σ_o W(o) × τ(o,p) × exp(3 × s(v,o)) × r_o
      / Σ_o W(o) × τ(o,p) × exp(3 × s(v,o))
b_p = clamp(Σ_{其他地点 q} (r_q − m_q) / (N − 1 + 5), −1, +1)
e_p = r_p − b_p − m_p
g_p = exp(−e_p² / 2)
c_p = k_p / (k_p + 2)
A   = (Σ c_p × g_p + 4) / (Σ c_p + 5)
γ   = clamp((A / 0.8)², 0.4, 1.25)
```

共识 `m_p` 中的 `o` 不含用户 `v`，也不含被封禁用户或自动生成的创建者/迁移评价。店主通过评价接口改评后（`source = 'user'`），可参与其他人的共识。`k_p` 是这些其他主动评价者的人数；`b_p` 只用其他地点估计评分偏差，避免当前地点影响自身偏差修正；残差 `e_p` 不截断。没有合格地点时，先验令 `A = 0.8`、`γ = 1`。贡献系数在 0.5–1 之间，一致度系数在 0.4–1.25 之间。

每次批处理先把所有人的 `γ` 设为 1，固定本批次的时间与证据快照，然后同步迭代 3 轮：由本轮 `γ` 计算全体 `W`，再用同一组 `W` 计算全体下一轮 `γ`；一轮全部算完后才切换到新值。第三轮结束后用最终 `γ` 计算并保存 `W`，更新全部评分的 `weight = W × τ`。禁止按用户逐个原地更新，以免用户顺序影响结果。

每天批处理一次；服务启动时若上次成功计算已超过 24 小时（或尚未计算）则补跑。新评价或改评直接写入该用户当前 `W` 作为 `weight`，因为这时 `τ = 1`；后续批次再统一刷新贡献、一致度和时间衰减。被封禁用户不作为评价者、共识证据或他人贡献的收藏/评价人数来源。

没有声誉记录的新用户默认 `W = 0.5`。重复提交相同评价不修改时间、来源或权重。旧 `M/D/YYYY H:mm[:ss]` 时间按北京时间解析，SQLite/ISO 中没有时区的标准时间按 UTC 解析；无效日期才使用迁移时间。已存在的评分记录和已撤回的迁移评价不会重新生成。

`0.8` 的先验中心、平方映射和 `0.4` 下限来自合成数据，后续应按真实数据校准。可在活跃评价者中至少 20 人的证据量 `Σ c_p ≥ 5` 时，检查这些人的 `A` 中位数是否接近 0.8，再决定是否调整。

## 按口味加权

登录且口味画像就绪（见 [PREFERENCES.md](../../preferences/doc/PREFERENCES.md)）时，另算一个只给自己看的平均分：

```text
μ          = 所有有效地点向量（归一化后）的平均
s(r)       = cos(用户向量 - μ, 评价者向量 - μ) × min(1, 我的画像地点数/5) × min(1, 评价者画像地点数/5)
口味权重   = exp(3 × s(r))            评价者没有可用画像时 s = 0，口味权重 1
总权重     = PlaceRating.weight × 口味权重
口味加权分 = Σ 总权重 × 分数 / Σ 总权重（不含自己的评价和被封禁用户）
```

- 为什么减去 `μ`：用户向量都是餐厅向量的加权和，原始余弦几乎都在 0.33–0.91（本地数据中位数 0.59），直接当权重等于人人一样。减去共同的“餐厅方向”后，相似度分布在约 -0.3 到 0.6，差异才显现。
- 画像只有一两家店时可信度打折，避免一家店的偶然重合主导结果；`exp(3s)` 让最像的人大约是最不像的人的十几倍权重，但不会完全忽略任何人。
- 其他评价者少于 2 人、或其中没有人有可用画像时不显示。评价者的画像按库中现有版本读取，由后台每分钟刷新。

## 每日次数

`PLACE_RATING_DAILY_LIMIT`（默认 10，1–1000）。按北京时间（UTC+8）自然日统计“今天新评或改评过的不同店铺数”：同一家店当天反复修改只算一次；重复提交相同评价不记录；撤回不返还次数；用完后仍可修改今天已评过的店、撤回任何评价。超出时返回 429“今天已经评价了 N 家店，明天再来吧”。被封禁用户不能评价（`requireAuth` 只放行只读请求）。

## API

均返回 `Cache-Control: no-store`。

- `GET /api/ratings/places/:placeId`：无需登录；带 token 时须通过完整 JWT/会话校验。返回

  ```json
  {
    "place_id": 12,
    "summary": { "count": 12, "average": 3.25, "tier": 3, "distribution": { "1": 1, "2": 2, "3": 4, "4": 5 } },
    "mine": { "score": 4, "source": "user", "updated_at": 1791968553027 },
    "personalized": { "average": 3.6, "tier": 4, "matched_raters": 5, "rater_count": 11 },
    "quota": { "limit": 10, "used": 3, "remaining": 7, "place_counted": false, "resets_at": 1792000000000 }
  }
  ```

  游客的 `mine`、`personalized`、`quota` 为 `null`。
- `PUT /api/ratings/places/:placeId`，`{ "score": 1–4 }`（严格整数）：评价或改评，返回同样结构。
- `DELETE /api/ratings/places/:placeId`：撤回自己的评价，返回同样结构。
- `POST /places` 可带 `rating`（1–4）作为创建者评价；不带时按标签默认。

## 用户画像

评价也是口味信号（用户向量算法 v2）：强烈推荐与收藏同权（5），均线之上记 2；均线之下 / 强烈拒绝表示明确不喜欢，该店不再作为兴趣来源（即使收藏或导航过）。迁移生成的创建者评价同样计入，所以添加过地点的用户上线后就有画像。

## 前端

- `frontend/src/places/rating.js`：四档定义、平均分 → 档位、避雷判断、创建者默认评价，与后端规则一致。
- 地点小卡（网页卡片与窄屏底部面板）显示“档位 分数 · N 人评价”，登录后附带“按你口味 x.x”和“我：xx”，点击打开 `PlaceRatingPanel`；详情面板有同样一行。
- 评价面板显示“综合分按评价者的贡献、一致度和评价新旧加权”，不显示个人权重。
- iOS 原生地点卡片：副标题最前面是“档位 分数（N 人）”，操作按钮多一个“评价”（评过时显示自己的档位），全屏详情里有“评价”一行；都打开网页评价面板，原生面板暂时让位。没有改 Swift 代码。
- 评价变化后，`frontend/src/map/MapView.jsx` 同步附近缓存、搜索/顺路结果与选中地点的评价字段，避雷图标立即更新。
