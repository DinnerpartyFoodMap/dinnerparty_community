# 画像可靠性与地图评分性能修复

最新画像编号格式和按实际视野预加载的修正见 [PROFILE_MAP_V4.md](../../preferences/doc/PROFILE_MAP_V4.md)。该后续修正涉及网页和 iOS 重新打包；本文件以下为上一轮优化的记录。

## 2026-11-05 日志修复

- `/api/visits/status` 曾因生产入口将整个路由挂在 `/api/visits/places` 而返回 404。现在挂载 `/api/visits`，查看、推断和回答操作在路由内使用 `/places/:placeId/...`，现有客户端操作地址保持兼容。回归读取生产入口的实际挂载路径，验证状态与查看操作均可达。
- 列表分页原先因 `AlgorithmClock` 或文本判断版本变化返回 409；后台成功生成画像、更新向量、登录资料变化也会导致这种变化。新增 `PlaceListClock` 仅跟踪原始地点内容、评分、文本来源、收藏与封禁/删除等变更；模型和文本判断的后台产物在当前两分钟列表内冻结，新列表使用最新结果。隐藏地点、屏蔽作者仍在每次翻页实时重查。评分变动仍要求重开列表。
- 网页与 iOS 共用列表组件遇到续页 409 时自动从第一页重开一次，并替换旧行；持续冲突停止重试，显示手动重试入口。过期、服务重启及进程内快照丢失均可恢复。快照仍在服务进程内，多个后端进程部署需会话粘滞才能稳定续页；本轮没有引入共享分页存储。
- 画像属性组整体为 `null` 或未返回时，按对应组全部未知处理。仍拒绝越界值、数字字符串、未知编号和长度不符数组；这些格式错误最多后台重提取一次。提取格式版本升至 3，旧失败任务不用等待旧退避。日志增加 `field=ds/rv` 与 `value_type`，不记录原始模型输出。本次日志只有 `expected_count=28`，无法仅凭这一项确认实际非法值是哪一种。
- 详情评分已有有效 active 本人预测时跳过旧版口味向量画像初始化和加权计算；预测不可用或关闭时继续旧版回退。没有更改模型、评分公式、首选加成或默认评价。

验证包括真实 HTTP 状态/查看请求、后台更新期间分页稳定性、评分及可见性变更撤销快照、浏览器 409 自动恢复及重试上限、画像未知组/格式修复/限流缓存，以及 active 预测不触发旧版计算。日志中的 1837.6ms 是一次成功请求的总耗时，不能从中推断服务器是否同步阻塞，也不能保证本轮优化后所有冷请求均低于该值。

部署：更新并重启后端，启动自动创建新时钟和触发器；更新网页静态包，iOS 重新构建安装包以包含分页恢复。私有服务和 4B 模型包无需更新或重训。

## 发现的问题

用户提供的 `snapshot.sqlite.gz` 解压后有 3546 个地点、3929 条评价、4341 条评价修订、474 个用户；350 个画像中 345 个失败、5 个成功，没有评论文本。诊断使用临时副本，不上传快照内容到模型服务。

画像错误原来统一输出 `Restaurant model profile extraction unavailable`，没有失败阶段。代码还错误复用了搜索意图扩展的默认 6 秒超时。本地用合成面馆输入调用真实 DeepSeek，另行复现了属性数组长度错误：要求 66 项，返回 65 项，导致整个画像失败。已改为按 `f00` 等编号输出属性对象，缺省项保持未知；兼容原先格式正确的数组，不猜测或修补错位数组。

原画像表触发器在失败次数、重试时间变化时也递增全局 `AlgorithmClock`，使未发生评分变化的地图/列表缓存反复失效。现仅在可读取的模型资产、输入哈希或状态变化时失效。已验证新失败行和重试计数不增加修订，实际画像内容变化仍增加修订。

网络调用已经使用 async/await；SQLite 和数值特征构建仍有同步部分。原地图请求为全部地点串行等待完整评分，评分还重复构造全局类别/属性统计、重复计算同一用户的历史偏好，并计算评级树根本不消费的首选特征。单纯添加 async 不能解决这些计算和缓存问题。

## 实现

- 地图 `/places` 和 `/places/nearby` 单次返回超过 `MAP_EAGER_RATING_LIMIT`（默认 100）时，延后模型评分。现有 `rating_count/rating_average` 及默认评价保留，模型字段暂为 null；详情卡原有评分接口继续获取两个评分。
- `MAP_EAGER_RATING_LIMIT=0` 延后全部地图标记评分，不改变详情、列表和随机推荐。
- 复用同一数据修订/模型/用户下的时间无关特征结构，仍为每个请求保留精确 `as_of_ms`。未来评价生效或跨过 30 天等边界时重新选取正确特征，后来的请求不会修改早先快照。
- 缓存历史类别和属性偏好，同一候选在公共、基线和本人预测流程内复用已计算特征。
- 原 v2/v3 评分/风险模型仅计算其消费的特征；首选排序继续计算完整 254 维特征。未知特征契约保留原完整路径。
- 每 25 个候选让出事件循环，缩短主线程连续占用。未声称全部数据库/CPU 运算已移入独立线程。
- 画像请求默认独立 60 秒超时；安全日志记录阶段、错误代码、HTTP 状态，不输出密钥、评论或上游原文。embedding 失败保留已验证画像和已成功向量，按退避重试缺失部分。

实际请求地图接口返回 3512 个可见地点，本机约 489 ms，模型批量评分调用为 0；3508 个地点保有原汇总评价。随后打开单点详情评分接口返回 200，两个模型字段均 active；冷启动约 2.59 秒，含原口味画像初始化。以上是本机单次诊断，不含真实设备绘制、生产网络和生产服务器负载。

真实云端画像冒烟仅使用合成面馆输入：修复后约 1.43 秒成功，产生 1024 维描述向量。没有向模型接口发送用户提供的快照数据。前端/iOS 沿用既有详情评分加载逻辑，本次无需重新打包；私有服务和已训练模型无需变更。

验证结果：65/65 后端测试文件通过；桌面/移动端评分界面回归通过。包含真实 HTTP 慢响应与限流重试、部分画像复用、安全日志、稠密地图延后计算、默认评价保留、跨时间边界缓存，以及评分/风险精简特征和完整特征逐字段一致性检查。
